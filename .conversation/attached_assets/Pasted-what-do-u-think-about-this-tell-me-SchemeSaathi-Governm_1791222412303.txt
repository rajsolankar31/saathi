what do u think about this tell me"# SchemeSaathi: Government Scheme Eligibility Engine

> A voice-first, regional-language assistant that tells people which government welfare schemes they qualify for, what documents they need, and where to apply.

**Status:** Planning / MVP design. The name "SchemeSaathi" is a placeholder; rename freely.

---

## Problem

India has hundreds of central schemes and many more state and district schemes: pensions, scholarships, health cover, housing, agriculture support, women and child welfare, disability aid, and more. Eligibility depends on combinations of age, income, caste category, gender, occupation, land holding, state, disability status, and family composition.

Millions of eligible people never claim their benefits because:

- They don't know a scheme exists.
- Criteria are buried in dense PDFs and gazette notifications.
- Information is mostly in English or Hindi.
- Rules change often and local variations are poorly documented.

## Solution

A person describes their situation in their own language, by **text or voice**. The system returns:

- A ranked list of schemes they likely qualify for
- Why they qualify (or don't)
- Documents required
- Where and how to apply
- Deadlines and next steps

## Existing Players and Our Gap

The government already runs **MyScheme** (myscheme.gov.in), and **Bhashini** provides open Indian-language speech and translation models. This project builds on that ecosystem.

| Area | What we add |
|---|---|
| Input | Conversational (text or voice), no long forms |
| Language | Regional-language-first for low-literacy users |
| Depth | State, district, and panchayat-level schemes |
| Action | Document checklists, "what's missing" view, reminders |
| Delivery | Assisted mode for field workers and NGOs |

## Core Design Principle

> **The LLM never decides eligibility.** It extracts and explains. Deterministic code decides.

- **LLM:** understands user input, reads scheme PDFs, writes explanations, translates.
- **Rules engine:** makes every eligible / not eligible decision.

## How It Works

1. User sends a text or voice message on WhatsApp or the web app, in their language.
2. A conversational agent asks only the questions that matter.
3. The profile is built progressively (no 30-field form).
4. The rules engine evaluates the profile against all schemes.
5. Results: **Eligible**, **Likely eligible (confirm X)**, **Not eligible (and why)**.
6. For each scheme: benefits, documents, where to apply, deadline.

## Rules Engine

Rules support `all_of`, `any_of`, and `not`. Evaluation uses three-valued logic: `True`, `False`, or `None` (unknown, because the user hasn't said yet). Unknown values drive which question to ask next.

```python
import operator

OPS = {
    "==": operator.eq, "!=": operator.ne,
    ">=": operator.ge, "<=": operator.le,
    ">": operator.gt, "<": operator.lt,
    "in": lambda a, b: a in b,
}

def evaluate(rule, profile):
    """Return True, False, or None (unknown)."""
    if "all_of" in rule:
        results = [evaluate(r, profile) for r in rule["all_of"]]
        if any(r is False for r in results):
            return False
        return None if any(r is None for r in results) else True

    if "any_of" in rule:
        results = [evaluate(r, profile) for r in rule["any_of"]]
        if any(r is True for r in results):
            return True
        return None if any(r is None for r in results) else False

    if "not" in rule:
        result = evaluate(rule["not"], profile)
        return None if result is None else not result

    value = profile.get(rule["field"])
    if value is None:
        return None
    return OPS[rule["op"]](value, rule["value"])
```

**Choosing the next question:** among unknown fields, ask the one that appears in the rules of the most still-undecided schemes.

## Ingestion Pipeline

1. **Collect** scheme documents from official portals and gazette notifications.
2. **Parse** PDFs (PyMuPDF; OCR or a vision-language model for scanned files).
3. **Extract** structured rules with an LLM, with a source quote for every rule.
4. **Validate** automatically: schema checks, plausibility checks, and a second-pass LLM cross-check.
5. **Human review** for low-confidence extractions and a random sample.
6. **Monitor** sources periodically and diff for changes.

Hand-encoded schemes serve as a gold test set to measure extraction accuracy.

## Conversation Layer

- **Understanding:** text goes straight to the LLM; voice goes through speech-to-text (Bhashini or Whisper-class) first. The LLM extracts profile fields from free-form input.
- **Questioning:** ask only what is needed, in the user's language.
- **Explaining:** turn rule results into plain language.
- **Honesty:** always show the source link and a "confirm with the office" note.

**Revenue** (citizens always use it free): B2G/CSR contracts, NGO licensing, API access for fintechs and insurers, and grants.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Stale or wrong rules | Source links, `last_verified` dates, change monitoring, human review |
| Wrong "eligible" answers | Deterministic engine, "likely" vs "confirmed" labels |
| Sensitive data exposure | Minimal collection, encryption, deletion on request |
| Local office variations | NGO partners and user feedback as ground truth |
| Overlap with government portals | Win on language, local depth, assisted delivery |
| Misuse by touts | Stay informational until official integrations exist |

## Privacy and Ethics

- Collect the minimum data needed; never store Aadhaar numbers.
- Treat income, caste, and disability data as sensitive.
- Encrypt data at rest and in transit; support deletion requests.
- Align with India's DPDP Act; get legal review before launch.
- Results are guidance, not a guarantee of eligibility.
